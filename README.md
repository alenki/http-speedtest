# http-speedtest

Консольная утилита для замера скорости скачивания. Делает 10 запросов к указанному адресу строго по очереди, дожидается полного ответа на каждый и печатает среднее время запроса, общий объём скачанных данных и скорость скачивания.

Node.js без зависимостей — только стандартная библиотека.

## Запуск

Нужен Node.js 20 или новее. Зависимостей нет, `npm install` не нужен. Склонируйте репозиторий и в его папке выполните (одинаково в Linux, macOS и Windows):

```bash
node speedtest.js https://speedtest.selectel.ru/10MB
```

Адрес — любой URL по http или https: тяжёлая картинка, архив, видео. Для осмысленного замера нужен файл от 10 МБ: на маленьком файле время уходит в основном на задержку, а не на передачу данных (подробнее — в разделе [«Как считается»](#как-считается)). Готовые тестовые файлы есть у [Selectel](https://selectel.ru/speedtest/): `https://speedtest.selectel.ru/10MB`, `…/100MB`, `…/1GB` (сервер в Санкт-Петербурге).

| Параметр | По умолчанию | Что делает |
| --- | --- | --- |
| `-n`, `--count <n>` | `10` | количество запросов |
| `-t`, `--timeout <сек>` | `30` | прервать запрос, если данные не приходят столько секунд |
| `--no-keep-alive` | выключен | открывать новое соединение для каждого запроса |
| `--json` | выключен | вывести результат в JSON — для скриптов и мониторинга |
| `-h`, `--help` | | справка |

Код выхода: `0` — все запросы успешны, `1` — хотя бы один запрос завершился ошибкой, `2` — неверные аргументы.

## Единицы измерения

- **Скорость — Мбит/с** (в выводе `Mbit/s`, мегабиты в секунду). В них провайдеры указывают скорость тарифа, а Speedtest, Яндекс Интернетометр и аналоги показывают результат, поэтому цифры можно сравнивать напрямую. В скобках та же скорость в **МБ/с** (`MB/s`, мегабайты в секунду): размеры файлов привычнее в байтах, так проще прикинуть время скачивания.
- **Объём** — точное число байт и то же в kB / MB / GB.
- **Время** — миллисекунды или секунды.

Приставки десятичные, как принято для сетевых скоростей: 1 Мбит = 1 000 000 бит, 1 МБ = 1 000 000 байт, 1 МБ/с = 8 Мбит/с.

## Пример

Замер на реальном интернет-подключении. В имени файла `100MB`, а на деле в нём 100 МиБ, то есть 104,86 МБ в десятичных единицах:

```text
$ node speedtest.js https://fsn1-speed.hetzner.com/100MB.bin -n 3
Speed test: https://fsn1-speed.hetzner.com/100MB.bin
3 sequential requests, keep-alive on, timeout 30 s

  #  status        size      time      ttfb            speed  connection
  1     200   104.86 MB   20.04 s    490 ms     41.86 Mbit/s  new
  2     200   104.86 MB   12.02 s     96 ms     69.80 Mbit/s  reused
  3     200   104.86 MB   16.12 s     99 ms     52.04 Mbit/s  reused

Requests        3 of 3 succeeded
Downloaded      314.57 MB (314,572,800 bytes) in 48.18 s
Average time    16.06 s per request (min 12.02 s, max 20.04 s)
Average TTFB    229 ms (1% of the request time)

Download speed  52.24 Mbit/s (6.53 MB/s)
```

Первый запрос открывает соединение (`new`), поэтому его TTFB — 490 мс против 96–99 мс у следующих, которые идут по тому же соединению (`reused`); в среднем же TTFB занимает лишь 1 % времени запроса. Скорость реального канала плавала от запроса к запросу (41,86–69,80 Мбит/с), а итоговые 52,24 Мбит/с — это общий объём, делённый на общее время, а не среднее трёх скоростей, которое дало бы завышенные 54,57 Мбит/с (подробнее — в разделе [«Как считается»](#как-считается)).

**Точность.** Проверена на локальном сервере, который отдаёт данные со скоростью ровно 100 Мбит/с и задержкой 30 мс: утилита показывает 96,2 Мбит/с, а недостающие ~4 % — это как раз доля задержки (TTFB) во времени запроса.

В терминале вывод цветной, и пока файл качается, обновляется строка прогресса. Если вывод перенаправлен в файл или в другую программу, это чистый текст без управляющих символов.

## Как считается

- **Время запроса** — от отправки запроса до получения последнего байта тела ответа. Сюда входят DNS, установка TCP- и TLS-соединения (если соединение новое), ожидание ответа сервера, редиректы и сама загрузка. **Среднее время** — суммарное время успешных запросов, делённое на их число. Таймер монотонный (`performance.now()`): переводы системных часов на замер не влияют.
- **Объём** — байты тела ответа, реально полученные по сети; заголовки HTTP не считаются. Тело не копится в памяти: байты считаются по мере поступления и сразу отбрасываются, поэтому файл может быть любого размера — замер трёх файлов по 1 ГБ укладывается примерно в 100 МБ памяти.
- **Скорость** = общий объём ÷ суммарное время запросов — то есть ровно «общий объём ÷ (среднее время × число запросов)».

  Это не среднее арифметическое скоростей отдельных запросов: такое среднее завышает результат, потому что быстрый запрос весит в нём столько же, сколько медленный. 1 МБ за 1 с и 1 МБ за 3 с — это 2 МБ за 4 с, то есть 4 Мбит/с, а среднее скоростей (8 и 2,67 Мбит/с) дало бы 5,33 Мбит/с.
- **TTFB** (time to first byte) — время до прихода заголовков ответа: задержка сети плюс время, пока сервер готовит ответ. Если на него уходит больше половины времени запроса, результат говорит скорее о задержке, чем о ширине канала, и утилита об этом предупреждает. Типичный случай — небольшая картинка: на канале 100 Мбит/с 100 КБ передаются за 8 мс, а ответа приходится ждать 30–50 мс.

В итог идут только успешные запросы; неуспешные видны в таблице и в строке `Requests`.

## Решения и почему так

- **Node.js без зависимостей.** Стандартной библиотеки хватает на всё: HTTP, разбор аргументов (`util.parseArgs`), тесты (`node:test`). Нечего устанавливать, обновлять и проверять на уязвимости; запуск — одна команда.
- **`node:http`, а не `fetch`.** `fetch` прозрачно распаковывает gzip и brotli — мы считали бы распакованные байты вместо реального трафика. Низкоуровневый модуль отдаёт тело как есть, умеет тайм-аут по неактивности сокета и сообщает, переиспользовано ли соединение. Цена — редиректы обрабатываются вручную (до 10, включая относительные `Location`).
- **`Accept-Encoding: identity`.** Просим сервер не сжимать ответ, чтобы мерить настоящие байты по сети: картинки и архивы и так не сжимают, а вот текст и JSON — да. Если сервер всё равно пришлёт сжатое, посчитаются сжатые байты — это и есть трафик.
- **Keep-alive по умолчанию.** Первый запрос платит за DNS, TCP и TLS, остальные идут по уже открытому соединению, как в браузере. Так мы меряем скачивание, а не рукопожатия. В таблице видно, новое соединение у запроса или переиспользованное; для сравнения есть `--no-keep-alive`.
- **Строго по очереди.** Следующий запрос начинается только после того, как предыдущий ответ дочитан до последнего байта: `await` в цикле, никакого `Promise.all`. Тесты проверяют это со стороны сервера — одновременно в обработке никогда не бывает больше одного запроса.
- **Ошибка не обрывает замер.** Ответ не 2xx, обрыв соединения или тайм-аут помечаются в таблице, итог считается по успешным запросам, код выхода — `1`. Исключение — первый запрос: если упал он, скорее всего, адрес неверный, и повторять его ещё девять раз бессмысленно.
- **Тайм-аут по неактивности, а не на весь запрос.** Большой файл на медленном канале может законно качаться несколько минут. Прерывать стоит только запрос, от которого N секунд не приходит ни байта.

## Тесты

```bash
npm test
```

57 тестов на встроенном `node:test`, интернет не нужен: локальный HTTP-сервер воспроизводит нужные условия — медленную отдачу, редиректы, gzip, обрыв соединения, зависание, ошибки сервера. CLI проверяется целиком, запуском отдельного процесса — так, как его запускает человек. CI (GitHub Actions) прогоняет тесты на Node.js 20, 22, 24 и 26 под Linux, а также под Windows и macOS.

## Структура

```text
speedtest.js      CLI: аргументы, вывод, коды выхода
src/measure.js    HTTP: замер одного запроса и серии запросов
src/stats.js      итоги: среднее время, общий объём, скорость
src/report.js     форматирование единиц и отчёта
tests/            тесты и локальный тестовый сервер
```

Замер, расчёты и вывод разделены: расчёты и форматирование — чистые функции без ввода-вывода, их легко тестировать отдельно от сети.

## Ограничения

- **Один поток.** Последовательные запросы по одному соединению могут не загрузить быстрый канал (от нескольких сотен Мбит/с) полностью, особенно при большом пинге. Поэтому Speedtest качает в несколько потоков; здесь последовательные запросы — условие задачи.
- **Первый запрос медленнее.** Кроме установки соединения, TCP в начале передачи «разгоняется» (slow start). На небольших файлах это заметно.
- Только HTTP/1.1; переменные окружения прокси (`HTTPS_PROXY`) не учитываются.
